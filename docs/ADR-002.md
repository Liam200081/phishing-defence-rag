1. 修订后的业务边界
第一版接受两种输入：
1. 钓鱼防御知识问题。
2. 用户提交的邮件文本或 .eml，以及“是否打开、点击、输入信息”等事件描述。
输出包含：
- 已知事实与尚未确认的信息。
- 邮件中可观察到的可疑迹象。
- 支持判断的邮件证据和知识来源。
- 与当前事实相符的响应建议。
- 必要的澄清问题或能力限制。
系统可以判断“存在这些可疑迹象”，但仅凭邮件文本不能确认账户已经失陷，也不能证明链接安全。
第一版必须实现	明确不进入第一版
知识问答与邮件分析两条路径	Identity Log Reader、Mail Log Reader

短期记忆与本地恢复	独立 Case Repository、Case revision 系统

这里的 “Incident Response” 指帮助理解事件并形成有依据的响应建议。产品说明和面试演示必须明确这一能力边界。
2. 架构选择：一个工作流、三个工具、有限恢复
默认流程：
输入 → 理解与规划 → 工具执行 → 证据汇总 → 必要澄清 → 回答 → 验证 → 返回结果
三个工具固定为：
- retrieve_knowledge
- parse_email
- analyze_iocs
不引入动态插件系统，也不提前建设通用工具平台。
LangGraph 负责条件分支、状态传递、暂停和恢复；RAG、邮件解析、指标计算仍是普通 Python 模块。
建议采用七个主要节点：
节点	职责	是否使用 LLM
Intake	校验输入、加载当前 Case、建立输入引用	否
Plan	识别问题类型、提取候选事实、提出任务和信息缺口	动态模式使用
Act	选择就绪任务，验证参数并执行工具	执行本身不用
Assess	更新证据、任务状态，决定继续工具、澄清或回答	规则为主
Clarify	提问并暂停，接收用户回复	问题可由 Plan 提出
Answer	根据事实、证据与问题类型生成回答	是
Verify	确定性检查和语义检查，产生结构化问题	混合


恢复路由是一个 Python 函数，不另造 “Recovery Agent”。
基本原则：节点数量不等于模型调用次数。 已有信息足够时直接回答，不为展示 Agent 能力强制执行所有工具。
3. Agent State 与 Memory：概念分离，存储从简
保留 Workflow State、Case State、Trace 的概念区别，但第一版不为它们建设三个独立系统。
状态字段	保存内容
case_id / run_id	案件和本次逻辑请求标识
request	当前问题、输入类型、邮件文件或文本引用
facts	已知事实、来源、状态和用户修正记录
plan	有限任务列表、依赖、状态和调整原因
tool_history	工具调用摘要、结果引用、错误与重试
evidence	邮件证据、IOC 观察、知识片段及来源
clarification	待问问题、阻塞字段、已问问题
answer	当前草稿、引用关系、最终回答
verification	检查结果、失败类型、关联断言
budget / status	调用计数、恢复计数、等待或完成状态


每项事实至少区分：
- user_reported：用户陈述。
- observed：工具从输入中直接观察。
- inferred：模型推断。
- unknown：尚不明确。
- superseded：已被后续纠正。
例如，用户先说“输入了密码”，随后纠正“只是打开页面”，必须更新当前有效事实，并使依赖旧事实的任务和草稿失效。无需引入完整版本控制系统，保留简短变更记录即可。
存储决定：
- LangGraph SQLite checkpointer：保存 Case 与运行状态。
- 每次运行一个结果记录：保存配置、答案、使用的证据和评测结果。
- 一份 JSONL trace：保存主要执行事件。
- 不建设独立 Case Repository 和 Artifact Store。
- 不建设长期向量记忆。
第一版一 Case 对应一个 thread_id。澄清回复恢复当前逻辑请求；新的独立问题创建新 run，但可以继续使用该 Case 的有效事实。
SQLite checkpoint 用于本地跨进程恢复；内存 saver 不足以实现重启恢复。LangGraph 官方持久化说明
恢复只保证从已保存状态继续，不宣称模型 API 调用绝不重复。第一版没有外部写操作，因此无需建设通用副作用事务系统。
4. Planner、Tool Registry 与 Executor 的最小实现
Planner
Planner 输出结构化任务，不输出长篇推理过程。每个任务只需要：
- Task ID。
- 要解决的问题。
- 工具名称和参数。
- 前置依赖。
- 完成条件。
- 状态。
- 关联证据。
典型计划：
场景	合理计划
“什么是 spear phishing？”	检索定义与区别
提交 .eml 并询问是否可疑	解析邮件 → 分析 IOC → 检索相关依据
用户表示点击后输入过信息	分析已提交材料 → 澄清影响建议的必要事实 → 检索响应依据
知识库没有某产品政策	明确知识缺口，不编造平台步骤


Python 校验任务是否使用已注册工具、依赖是否有效、参数是否完整、数量是否超限。
重新规划只用于：
- 用户纠正了关键事实。
- 工具结果使原调查方向不适用。
- 原计划无法解决当前目标。
单纯引用错误不需要重新规划。
Registry
一个静态工具表即可，记录名称、说明、输入输出类型、超时和是否可重试。不建立插件发现、权限继承或动态注册机制。
Executor
一个统一执行入口，负责：
1. 工具名称和参数校验。
2. 调用工具。
3. 超时与有限重试。
4. 返回统一结果。
5. 写入 trace。
工具状态至少区分 ok、no_result、error。不能把工具报错解释成“没有风险”。
重复调用检测采用“工具名 + 规范化参数 + 相关数据版本”。输入未变且已有有效结果时复用结果；超时结果不作为成功缓存。
建议初始上限
以下是待校准的开发默认值，不是实验结论：
控制项	初始上限
计划中的工具任务	4
总工具调用次数，包含重试	6
总 LLM 调用次数，包含修复	8
额外知识检索	1 次
重新规划	1 次
回答修复	1 次
同一逻辑请求的澄清轮次	2


所有节点共用预算，clarification resume 不重置预算。达到上限时输出有依据的部分结论和未决问题。
5. 三个工具的开发契约
工具	输入	输出	验收重点
retrieve_knowledge	查询、可选来源限制	片段、文档/页码、chunk ID、分数、索引版本	来源可定位，生成上下文不丢失关键证据
parse_email	邮件文本或本地 .eml 引用	From、Reply-To、Subject、正文、链接、附件元数据及解析告警	真实 MIME 邮件可解析，字段缺失不崩溃
analyze_iocs	解析出的 URL、域名等	规范化指标、静态观察、关联原始位置和限制	不联网、不执行内容，不把启发式判断当成恶意定论


补充边界：
- parse_email 不加载 HTML 外部资源。
- 邮件内携带的认证结果先作为“邮件中出现的声明”，不能自动当成已验证的真实性证据。
- analyze_iocs 可以比较显示链接和实际目标、识别 IP 形式主机名等结构特征，但不输出伪装成概率的风险分数。
- 附件只提取元数据，不解压运行或做沙箱检测。
RAG 改造必须保留的内容
现有 PDF、Chroma、清洗消融和逐题评价继续使用。重点修改：
1. 显式指定 embedding 配置。
2. 补齐来源和页码。
3. 统一 Context Builder，移除固定 [:300] 作为默认策略。
4. 保存实际发送给模型的上下文。
5. 将知识检索与最终回答生成分开。
6. 保留旧指标供历史对比，同时修正新评测的证据口径。
读取相邻片段可以作为检索工具的内部能力，不必再增加第四个工具。
6. Clarification 与 Verification 的执行规则
必须澄清的情况
仅当缺失信息会影响当前判断或建议时提问，例如：
- “打开了邮件”与“点击链接”含义不清。
- 是否输入敏感信息存在冲突。
- 用户要求平台特定操作，但没有说明平台。
- 用户更正了关键事实，原计划已失效。
不因为普通字段缺失就提问；不能通过无限澄清回避任务。
Verification 分两层
确定性检查：
- 回答是否为空或被截断。
- 引用 ID 是否存在。
- 工具是否实际成功。
- 是否仍使用已被纠正的事实。
- 是否把建议描述成已经执行。
- 是否违反调用与循环上限。
语义检查：
- 是否回答当前问题。
- 关键断言是否有证据支持。
- 是否编造组织或产品特定政策。
- 建议是否与用户报告的情况一致。
- 是否表达必要的不确定性。
Verifier 返回 Finding → Failure Type → Recovery Action，不只返回一个分数。
失败类型	恢复动作
检索结果有依据，但上下文遗漏	重新构造上下文
缺少知识依据	定向补检索
缺少用户事实	Clarification
新事实改变任务方向	Replan
证据充分但回答表述错误	Repair answer
工具暂时失败	有限重试
无进展或预算耗尽	输出受限回答和明确缺口


不允许所有失败统一重试整个 Agent。

首版数据规模

- 用户初始输入。

- 允许的工具动作。
- 成功条件。
- 禁止出现的错误断言。
- 预期最终状态：完成、证据不足或需要澄清。
必须覆盖：
场景	测试能力

点击链接但未输入信息	差异化建议

知识库没有该产品政策	Grounding 与不确定性
正常邮件具有复杂 HTML 或多个链接	避免只凭表面特征下结论
邮件包含要求忽略系统指令的文本	不可信数据边界
工具 timeout	故障处理
同一 IOC 重复分析	重复调用控制
Q8 定义位于字符 300 之后	上下文回归
生成被截断或返回空内容	输出完整性检查


数据真实性声明必须准确： 邮件正文来自真实样本；用户点击经历和后续纠正可以是脚本化场景，但必须明确标注。不能把这种组合包装成真实发生过的完整安全事件。
正常评测实际运行邮件解析、IOC 分析、Chroma 和模型。Mock 只用于故障注入、离线单元测试及固定用户回复，不替代核心工具。
8. Evaluation：只维护三个核心 KPI
核心 KPI	定义	防止误用
Case Success Rate	满足该 Case 预定义成功条件，且没有关键错误的 Case 占比	正确承认证据不足可以算成功；盲目拒答不算
Evidence Support Rate	经标注或复核，得到事实/知识证据支持的关键断言占比	引用存在不等于支持；无断言记 N/A，不能记满分
Cost per Successful Case	全部运行成本，包括失败与修复，除以成功 Case 数	无价格记录时报告 token 消耗；成功数为零时标为不可计算


辅助诊断只保留：
- 总调用数、重复调用数。
- 必要/不必要澄清案例。
- Reflection 检出、误报和修复案例。
- 活跃执行时延，用户等待时间单列。
- legacy CR、AR、Faithfulness proxy。
- 失败类型分布。
辅助指标用于解释问题，不单独建设 Dashboard。
小样本结果报告分子、分母和逐案例表现。不能只展示一个百分比，更不能预先承诺 Agent 一定提升多少。
9. 对照实验：保留 B0 → B1 → W0 → A1，并实际完成小型 Multi-Agent 实验
版本	内容	回答的问题
B0	原始 RAG 与历史结果	当前起点是什么
B1	修复上下文、来源和输出记录的单轮 RAG	基础修复带来什么变化

比较规则：
- 原十题用于 B0/B1/W0/A1 的知识问答回归。
- 事件场景中，W0 与 A1 使用相同工具、样本和用户回复脚本。
- B1 无主动调查能力，其结果作为能力基线，不将信息差全部归功于 Planning。
- 固定模型、prompt 版本、知识库快照和预算。
- 对保留集进行重复运行，记录波动。
- 历史 Excel 保留，但不假装它具备完整实验溯源。
A2 的明确范围
只实现两个角色：
- Analyst：主流程，负责分析与初稿。
- Reviewer：拥有局部状态，检查一项关键结论；可自主决定是否进行一次补充知识检索，返回 findings 和证据。
Python 负责合并和最终路由。Reviewer 不直接修改共享事实，不建设 Agent 通信平台，不加入第三个角色。
A2 与 A1 在相同的总调用和 token 上限下比较，双方都计入验证成本。Reviewer 必须具有独立的局部任务和受限工具决策，不能只是把普通 verifier 改名为 Agent。
这个实验是后期交付项，不从计划中删除。 但它不阻塞 A1 的首版演示，也不自动成为默认架构。即使结果没有收益，也应如实保留。

11. 开发顺序：六个可独立验收的里程碑
M1｜保留基线并修复 RAG
- 开发内容： 冻结历史结果；提取核心函数；统一配置；补来源、实际上下文、响应终止信息；修复截断和问题类型冲突。
- 验收标准： Notebook 与 CLI 调用同一实现；原十题可运行；历史结果不被覆盖；Q8 证据可进入上下文；空回答和截断被显式标记。
- 测试方式： 固定响应回归、Context Builder 边界测试、导出回读。
- 产物： B1、基础测试和可追溯结果。
M2｜真实邮件数据与三个工具
- 开发内容： 采集并锁定样本；编写事件 Case；实现 parser、静态 IOC 分析和知识工具契约。
- 验收标准： 数据来源可重建；24 个 Case 有明确成功条件；正常测试真实执行三个工具；至少覆盖事实纠正、知识缺失和正常邮件对照。
- 测试方式： 真实邮件 fixture、字段提取断言、IOC 去重与原文映射、无网络行为检查。
- 产物： 数据 manifest、Case 集、工具实现。
M3｜固定 LangGraph Workflow 与本地状态
- 开发内容： 使用固定路径接入工具；保存 facts/evidence；加入规则澄清和 SQLite checkpoint。
- 验收标准： 形成 W0；两个 Case 状态不串；澄清后可恢复；重启可继续；新用户事实正确进入状态。
- 测试方式： 固定工具结果的路径测试、暂停恢复、事实纠正测试。
- 产物： 可演示的状态工作流。
M4｜有限 Planning 与 Reflection
- 开发内容： 加入动态计划、工具路径选择、Verifier 和分类恢复。
- 验收标准： 形成 A1；简单问答不强制解析邮件；重复调用受控；用户纠正使旧结论失效；补检索、澄清和修复走不同分支；达到预算必定终止。
- 测试方式： 场景集、故障注入、非法计划/参数、同一失败反复出现测试。
- 产物： 单 Agent 主线和可检查 trace。
M5｜统一评测、消融与失败分析
- 开发内容： 运行 B1/W0/A1 对照，保留清洗消融，增加 Planning/Reflection 开关实验。
- 验收标准： 报告三个核心 KPI、成本及逐 Case 失败；每个数字能找到运行记录；不删除失败样本；不能用 legacy proxy 代替事实支持评价。
- 测试方式： 指标人工核算、同一保存结果重复评分、保留集重复运行。
- 产物： 面试可解释的实验报告和失败案例。
M6｜小型 Multi-Agent 实验与交付说明
- 开发内容： 增加受限 Reviewer 子流程，完成 A1/A2 同预算对照；整理运行步骤和设计取舍。
- 验收标准： A2 默认关闭；报告收益与额外成本；无收益也保留结论；无密钥可跑离线测试，有密钥可运行真实模型演示。
- 测试方式： Reviewer 错误结论、补检索失败、预算耗尽、局部状态隔离。
- 产物： Single-Agent / Multi-Agent 消融与最终 README。
开发过程中每个里程碑单独提交，先通过该阶段测试再进入下一阶段。不同时引入 LangGraph、Planner、Verifier 和 Multi-Agent。
12. 决策理由、trade-off 与最终完成标准
为什么采用这个架构
它直接回应当前项目缺陷，并让岗位相关能力落实到可测行为：
能力	可展示行为
Planning	不同输入采用不同任务计划，事实变化后局部重规划
Tool Use	选择并执行真实的解析、分析和检索工具
Memory	用户纠正后不再沿用旧事实
State Management	澄清和重启后继续同一 Case
Reflection	根据失败类型选择不同恢复动作
RAG	来源明确、上下文可追踪、保持既有消融
Evaluation	区分基础修复、工具流程与自适应策略的贡献
Multi-Agent	同预算实验检验协作价值
性能与成本	全流程有界，记录真实消耗


为什么不直接使用复杂 Multi-Agent
当前只有一个事件目标、三个工具和一个主要知识域。多角色通信、共享状态协调和复杂合并没有足够业务价值。保留一个小型实验已经能证明理解协作设计和成本取舍。
未来如何扩展
当真实业务出现独立证据域或不同工具权限时，可以把现有任务变成子工作流。子流程返回结构化 findings 和 evidence IDs，由主流程合并；不需要重写整个系统。
真实邮箱、身份日志和写操作接入属于新的 ADR，不能作为当前工具接口中的“顺手扩展”。
Trade-off / 风险	当前处理
静态分析无法确认实时威胁	明确输出观察与限制，不承诺检测平台能力
SQLite 不面向多用户并发	接受本地单用户边界
小样本不能证明泛化能力	报告样本数量、逐案例表现与重复运行结果
真实邮件不提供真实用户行为	明确区分真实邮件和脚本化事件历史
LLM verifier 可能共享生成器偏差	确定性检查优先，人工复核核心评价
Agent 增加成本但未提升质量	保留 W0/B1 比较，按结果选择默认模式
恢复可能重复模型请求	记录尝试，不宣称 exactly-once
架构再次膨胀	新增连接器、数据库或角色必须说明哪条现有测试无法满足


项目完成不以“Agent 一定优于 RAG”为条件，而以下列交付为条件：
- 核心工具真实运行，数据来源和脚本化部分明确。
- 关键确定性回归测试全部通过，预算内必定终止。
- 已知截断、上下文错位和事实纠正问题有回归测试。
- 一次回答能追溯到计划、工具、证据和验证。
- B1/W0/A1 的对照结果完整，失败样本没有被隐藏。
- 完成小型 A1/A2 实验，默认架构选择有证据。
- 面试官能够按 README 运行，并从一条失败案例追问到具体原因、修复和验证结果。
