# M5 评测运行与复核

所有命令在项目根目录运行。`run` 使用同一份 `evaluation/m5_config.json`、知识索引、模型、prompt 和 Case 清单。M5 配置统一提高上下文预算，以容纳真实邮件与知识证据。B1 只获得问题及知识检索；W0/A1 获得相同邮件和固定用户回复。`A1-no-planning` 与 A1 只差 Planning 开关；`A1-no-reflection` 与 A1 只差 Reflection 开关。规划是现有确定性计划，没有额外 LLM 调用。W0 的查询固定；A1 根据已确认用户事实调整知识查询。Reflection 使用现有验证与分类恢复路径。模式按 Case 交错，首个模式随 Case 和重复轮次轮换；`execution_order` 保存真实执行顺序。

```sh
PYTHONPATH=src .venv/bin/python -m phishing_agent.eval_cli run --suite event --split development --modes B1 W0 A1 A1-no-planning A1-no-reflection --min-interval-seconds 15 --retry-429 2
PYTHONPATH=src .venv/bin/python -m phishing_agent.eval_cli run --suite event --split held_out --modes B1 W0 A1 A1-no-planning A1-no-reflection --repeat 2 --min-interval-seconds 15 --retry-429 2
PYTHONPATH=src .venv/bin/python -m phishing_agent.eval_cli run --suite knowledge --modes B1 W0 A1 --min-interval-seconds 15 --retry-429 2
```

正式运行需要干净的 Git 工作区，并先向同一模型做最小服务探测；探测失败则不启动批次。输出位于 `experiments/m5/<run_id>/run.json`，包含每个 Case 的最终状态、回答、证据、逐步 checkpoint、每次模型尝试的 HTTP 状态、重试、usage、配置、代码与知识快照指纹。该目录被 Git 忽略，原始邮件可能出现在 trace 中。旧提交或 dirty 工作区的运行不得充作当前正式验收证据。运行前在 development 调试；holdout 只作固定条件的最终评估，不据此调规则或阈值。正式运行遇到模型服务错误会停止并保存 `partial.json`；该文件不得用于 KPI 对照。每日 token 配额错误不反复重试。服务端错误和缺失 usage 必须保留，不能把它们算作零成本或作为策略效果。若正式批次被服务错误污染，应在相同模型、数据、配置和评分规则下整体重跑，旧批次仍保留。故障注入 Case 保留在结果中，并在场景字段标识；解释业务成功率时应明确列出其影响。

## 冻结的人工复核口径

- 按 Case 原文逐项判定 `success_conditions`，并检查 `forbidden_key_assertions`。最终状态依照 Case 的 `expected_result_status` 判断；正确说明证据不足可满足相应 Case，空泛拒答不满足。
- 将回答拆成可独立判真的关键事实断言；建议性措辞和纯流程说明不充当事实证据。每条断言记录回答原文、支持/不支持、理由；支持时记录保存证据的 ID 和原文摘录。用户脚本事实只由用户输入或固定回复支持，邮件源标签不能直接证明恶意或安全。
- 无关键事实断言记零个断言，Evidence Support Rate 为 N/A。引用 ID 有效但内容不蕴含断言，仍判不支持；引用失效不得判支持。
- 失败类型只从 `retrieval/context`、`planning`、`tool routing/execution`、`fact/state`、`clarification`、`verification/reflection`、`budget/termination`、`answer/grounding`、`service/provider` 中选。原因必须能在所列 `trace_refs` 事件中核验，包含对应工具、计划、事实、澄清、验证、预算、回答或服务调用。模型 API 限流/错误标为 `service/provider` 运行有效性问题，不能解释为 Agent 能力不足。
- reviewer 不修改 Case、成功条件或模型输出。逐 Case 复核文件与所用 run ID、评分文件指纹一同留存；holdout 结果只能按此口径评分。

质量判断必须使用人工复核 JSON 列表。每条 review 按 `run.json` 的 `repetition`、`mode`、`case_id` 对齐，并包含：

```json
{
  "repetition": 0,
  "mode": "A1",
  "case_id": "PP-1-1",
  "expected_result_status": "complete",
  "status_met": false,
  "status_reason": "<将最终状态及回答与预期比较>",
  "conditions": [
    {"text": "<原 Case 的成功条件原文>", "met": false, "reason": "<引用回答或 trace 的复核理由>"}
  ],
  "critical_error": false,
  "claims": [
    {"text": "<回答中的关键断言原文片段>", "supported": false,
     "reason": "<复核理由>", "evidence_refs": []}
  ],
  "failure": {"type": "answer/grounding", "reason": "<可验证原因>", "trace_refs": [0]}
}
```

每个预定义成功条件必须逐项复核。`claims` 对所有关键事实断言逐条标注；无关键断言时留空，Evidence Support Rate 为 N/A。判为支持的断言需要保存实际证据 ID 与 `evidence_quotes`，每段必须是该证据中的原文；引用存在但内容不匹配会被拒绝。`critical_error` 为真时还需 `critical_error_reason`。失败项必须记录 `failure.type`（八个限定类型之一）、原因与至少一个真实 `trace_refs` 索引。评测程序不能自行推测失败根因。

```sh
PYTHONPATH=src .venv/bin/python -m phishing_agent.eval_cli score experiments/m5/<run_id>/run.json --reviews /path/to/reviews.json
```

评分入口默认核对当前 HEAD、工作区状态、源码树和配置指纹；如需重评分历史 run，必须显式使用 `--allow-historical`，报告中标明版本。评分写入同目录的 `score-<review_sha256>.json`，相同复核重复评分不覆盖文件，不同复核版本分别保存。未复核的 Case 会保留在结果中，核心 KPI 的比例值为 `null`，不会伪装为成功或失败。成本使用全部运行的 token 总量（包括失败调用中服务商返回的 usage）；若某次调用无 usage，则成本不可计算并标注 `usage_incomplete`。无成功 Case 时成本标注 `not_computable_zero_success`。服务探测 usage 单独记录为运行开销，不归因于任何模式。结果报告包含逐 Case、分子/分母、重复运行的成功率范围和按类型定位到 trace 的失败清单。Legacy proxy 只作为 diagnostic。小样本与单次运行不能据此断言 A1 优于其他模式。
